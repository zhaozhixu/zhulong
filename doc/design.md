# Zhulong: A Lisp-Hosted Large-Model System

Named for Zhulong (烛龙), the Torch Dragon of the *Classic of Mountains and Seas*, whose open eyes are day and whose closed eyes are night, the dragon that wields the torch.

---

## 1. Background and Positioning

Large-model infrastructure is converging on a "functional programming plus compilers" shape. JAX builds on pure functions and composable function transformations; PyTorch is moving the same way through torch.compile and torch.func. The underlying force is scale: the larger the system, the more it depends on a compiler with a whole-program view to perform operator fusion, automatic parallelization, and memory planning — and whole-program optimization demands the purest possible program representation. This convergence gives Lisp a genuine opening. S-expressions are a bare abstract syntax tree, so programs can be inspected, transformed, and verified as data — a natural fit for an era in which code is increasingly generated, manipulated, and checked by machines. Macros and language-oriented programming make restricted DSLs nearly free to construct, providing precise, minimal notations for model structure, rewrite rules, parallelization strategy, and orchestration. And REPL-driven, image-based development offers something rarer: the possibility of extending an interactive development style into a runtime capability — a model system that can be observed and modified while it runs.

The opening is real; so are the constraints. The performance moat of inference sits in CUDA-level kernel engineering, where the host language contributes nothing distinctive. Mainstream frameworks have already absorbed the essentials of functional design. And niche languages remain at a corpus disadvantage for LLM-assisted coding. Taking these constraints seriously, the project's core positioning is: **do not build the heavy-compute part of the runtime; build only the brain.** Racket owns the "thinking" layers — model definition, symbolic optimization, and execution orchestration — while all heavy computation is delegated to libtorch operators and to artifacts compiled by AOTInductor/Triton. The project's measure of value is not throughput numbers but iteration speed: whether it can explore optimization strategies and interactive capabilities that existing toolchains cannot. It is first a research vehicle, and simultaneously a foundation for natively compiled, distributable applications.

## 2. Design Overview

### 2.1 The Three-Plane Architecture

The system consists of three planes, each answering one question.

**The definition plane answers "what is the model."** It comprises a shallowly embedded model-definition DSL with two backends (eager for immediate execution, tracer for graph capture), stage-polymorphic control flow (data-dependent branches and loops lift into the graph automatically), a safetensors weight loader, an S-expression graph IR carrying type and provenance annotations, and KV-cache state modeled by linear threading. Its output is a computation graph suitable for machine transformation, together with a set of definitions a human can execute and debug directly — two views of the same code.

**The optimization plane answers "what is the best way to compute it."** It is a pass pipeline over a single IR: equality-saturation rewriting performs semantics-preserving transformation; parallel planning decides sharding and device placement and materializes communication as graph nodes; communication scheduling arranges the overlap of asynchronous communication with computation. The passes exchange information through annotations on the IR, and bottlenecks discovered by the scheduler can feed back into the planner to trigger re-sharding. Parameter search is not a pass in the pipeline but a tuning loop around it, supplying measured data to each pass's cost model. The rewrite pass's rule library starts hand-written and is enumerated early; LLM-in-the-loop rule proposal is its long-term growth mechanism. The plane's output is an execution plan: an optimized, scheduled graph partitioned into compiled subgraphs and interpreted glue.

**The execution plane answers "how to lay it onto hardware."** Bottom-up: the FFI bridge (PyTorch's Stable C ABI first, generated wrappers for gaps), the dual-mode execution mechanism (every subgraph can switch between interpreted and compiled execution), the compilation service (a build-time Python sidecar producing C-ABI artifacts via AOTInductor; zero Python at runtime), the multi-stream task-DAG executor, and, on top, lazy-stream orchestration. Orchestration and the multi-stream executor are schedulers at two different timescales. Orchestration manages request- and token-level control flow at millisecond scale — which request steps next, how to sample, how to batch — and lives in Racket. The multi-stream executor decides, at microsecond scale, in what order and on which CUDA streams the subgraph DAG of a single step is launched. Orchestration says "execute one step"; the executor lays that step efficiently onto the hardware.

Cutting across all three planes is a tiered observation and hot-reload capability: tier A, a read-only observation window (probes, cross-checking, profiling), depends only on the eager backend and stream transformers and ships early; tier B, writable hot reload (redefining model layers in a running system), depends on provenance and invalidation machinery and ships together with the rewrite engine.

### 2.2 Host Language

The host language is Racket on the Chez Scheme backend. Each reason maps to a concrete need. Racket CS compiles to native machine code through Chez; raco exe and raco distribute produce standalone native executables, meeting the hard requirement of application distribution. ffi/unsafe provides a mature C FFI for binding the Stable C ABI. The #lang mechanism lets the model DSL and the rule DSL be genuine languages rather than piles of macros. Chez's incremental compilation and runtime code loading are the substrate for the observation and hot-reload capabilities. The host remains dynamically typed; the design does not depend on Typed Racket — as explained later, the only "type checking" required is a linearity constraint on the IR, not on Racket source.

### 2.3 Non-Goals and Long-Term Outlook

The current version explicitly does not: write CUDA kernels by hand (Triton-generated ones excepted), introduce a second compiler IR such as MLIR or TVM, or compete with vLLM/TensorRT-LLM on production throughput. The roadmap contains no integration with external inference engines — the system is built bottom-up, each layer resting on its own foundation.

Training and automatic differentiation are long-term goals rather than permanent exclusions. Autodiff is fundamentally a graph transformation — differentiating S-expressions is a classic Lisp exercise — and backward graphs are just as amenable to the eqsat-plus-planning pipeline. The current architecture reserves a place for it without implementing it. Also long-term: cross-node distribution (NCCL integration) and a direct Triton emission path.

## 3. The Definition Plane

### 3.1 Shallow Embedding and Trace Semantics

Model definition uses a shallow embedding: DSL operators (matmul, softmax, rms-norm, and so on) are ordinary Racket generic functions, dispatched on the "current tensor backend" parameter. Under the eager backend, an operator call executes immediately via FFI and returns a real tensor. Under the tracer backend, an operator call merely records a graph node and returns a symbolic placeholder tensor. The same model code switches between "run now" and "build a graph" by switching the backend:

```racket
#lang zhulong

(define-layer (rms-norm x #:eps [eps 1e-6])
  (let ([v (mean (sqr x) #:axis -1)])
    (* x (rsqrt (+ v eps)))))

(define-model (llama-block x cfg)
  (let* ([h  (+ x (attention (rms-norm x) cfg))]
         [h2 (+ h (mlp (rms-norm h) cfg))])
    h2))
```

Trace semantics deserve a precise statement: **tracing is "executing once, with recording" — not a separate compilation phase.** When a definition is written, no graph exists yet. The graph comes into being when the model function is called once under the tracer backend, with symbolic tensors carrying only shape and dtype. Graph-construction logic runs as ordinary Racket code — loops really loop, configuration-dependent branches really branch, higher-order functions compose as usual — and every operator call is recorded as a node. Each model configuration is traced once; thereafter the graph is reused token after token. Shallow embedding plus tracing is chosen over deep embedding (macros expanding the DSL directly into IR) because the former allows graph-construction logic to be written in full Racket, whereas the latter would confine it to forms the macro system can understand. This is the design sweet spot JAX has validated.

The trace is also an online partial evaluator, which gives a precise disposition to the non-tensor logic mixed into model code: stage information lives in values, not in syntax — a host value means "now," a symbolic tensor means "later" — so the mixture needs no syntactic wall. There are five destinations. Host computation that never touches tensors (looping over a configuration, dispatching on a variant name) runs at trace time and evaporates, leaving only the graph structure it selected. Host values flowing into tensor operations (eps, precomputed frequency tables) are baked into the graph as constants. Host scalars that vary per invocation (the position, the cache's current length) must not be baked: they enter the step as 0-d tensor inputs — the generalization of the shape policy's "position as data," and the reason this design needs no SymInt-style machinery: shapes are already static, and everything that varies travels as data. Tensor values flowing toward host decisions are taken over by stage-polymorphic control flow (3.2); genuine host effects cross the boundary explicitly (3.2). The one insidious hazard here is stale capture: a closure captures mutable host state, and the momentary value read during tracing is silently baked into a constant — the classic JAX trap. Three lines of defense: by discipline, per-invocation values must arrive through arguments, never through ambient state; by tooling, the trace report includes a constant audit listing every baked constant with its provenance (provenance thereby extends from nodes to constants, and trace invalidation on configuration change depends on it); by mechanism, reads of mutable host state during tracing can be instrumented to warn.

A trace fixes tensor shapes, so shape variability must be planned explicitly — and the two phases of inference differ in kind. **Decode is static by construction.** Every decode step consumes exactly one token; the quantity that grows — context length — lives inside the cache, and the cache arena is preallocated at max-len: the buffer's shape is invariant from the first step to the last, while the current length enters the kernel as a scalar position index — as data, not as shape. Every decode step therefore presents identical shapes, which is also precisely what makes whole-step CUDA-graph capture possible (5.3). **Prefill is genuinely dynamic.** The prompt arrives as a `[1, L]` tensor whose `L` differs per request: the varying quantity is the size of the input itself and cannot be hidden as data, while padding every prompt to max-len is ruled out by attention's O(L²) cost. Prefill therefore compiles through AOTI dynamic dimensions (the sequence dimension marked dynamic), with length bucketing retained as the fallback in case shape-generic kernels measure slower than static specialization — both paths are kept, and the choice is settled by measurement. Prefill is deliberately not captured as a CUDA graph: its shapes rarely recur, and its few large kernels amortize launch overhead on their own — the opposite of decode's thousands of small launches.

Models are never imported from external formats. ONNX and torch.export cannot keep pace with the structural evolution of large models, and aligning to external operator semantics is an endless chase. More fundamentally, only by owning the definition layer do runtime observation and hot reload become possible: an imported graph is dead; a natively defined model is live code. The operator vocabulary tracks ATen, initially scoped to Llama-family decoder-only architectures and their common variants, with RoPE, GQA, RMSNorm, and MoE routing provided as library components so that a new variant costs under a hundred lines to define — library components are written, per industry practice, in branch-free dataflow form (mask/padding, top-k plus gather/scatter); this hand-written authoring layer is the primary eliminator of the branches that matter (3.2). Where useful, an LLM can semi-automatically translate reference implementations (e.g., HF transformers) into the DSL — S-expressions are exactly the output format easiest to machine-generate and machine-check. Weights are loaded by parsing safetensors directly (an eight-byte header length, a JSON metadata block, raw tensor bytes) and zero-copy mapped into libtorch tensors via FFI. A distributed native binary therefore ships with only the libtorch shared library, compiled artifacts, and weight files — no Python anywhere.

The operator vocabulary has one organizing rule. An operator's identity is a symbol, and that symbol threads the whole system: the definition plane's registry, each backend's implementation table, the reference generator and the parity manifest, and — once the graph IR lands — the node's op field are all keyed by the same name. The registry records only backend-neutral semantic facts — the shape rule and the dtype rule, the operator's portable contract; knowledge tied to a particular backend or piece of hardware (eager implementations, FX emission, capability manifests, measured costs) forms separate facet tables keyed by the operator name, and never flows back into the registry. The call shape is uniform: operands are positional, attributes are keywords, and an attribute's key is its parameter name; the registration and implementation sides are written as mirrored declaration forms that derive keys from parameter names, so agreement holds by construction rather than by discipline.

Operator identity is device-neutral: the vocabulary contains no cpu-matmul versus cuda-matmul. Device is a property of data and of placement — under eager execution operators follow their inputs' device and cross-device movement is an explicit operator; on the graph, placement is an annotation written by the planning pass (4.2), and lowering partitions subgraphs along it, materializing transfers at cut edges. Device stays out of identity for three reasons: placement is a decision variable of the optimizer, and baking it into identity would freeze it before optimization begins; shape/dtype rules and rewrite rules are device invariants, so duplicating the vocabulary per device doubles the cost of every table and rule for zero semantic gain; and per-microarchitecture differences in implementing one operator are either a choice among equivalent forms (the cost model, fed by per-target measurement, decides at extraction) or in-kernel tuning (delegated to the compilation stack) — both live below the vocabulary. The precedent is ATen's own dispatcher: one operator name, kernels selected by dispatch key.

Numeric precision is a first-class commitment rather than an afterthought: **bf16 is the native path from phase one.** Llama-family weights are published as bf16 safetensors, and zero-copy loading yields bf16 tensors directly; eager execution, compiled artifacts, and the cache default to bf16 throughout. "Matching the reference implementation" is accordingly a statement about test methodology, not about system dtype: layer outputs are compared against an fp32 HF reference under per-layer tolerances, since bit-exactness under bf16 is unattainable for legitimate reasons — accumulation order and kernel selection differ. Quantization is in scope, positioned as a weight format plus an extension of the operator vocabulary rather than a separate subsystem: weight-only int8/int4 comes first (decode is memory-bound, so dequantize-fused matmul buys the most), with kernels delegated to torchao bindings or AOTI/Triton generation — the no-hand-written-CUDA rule stands; fp8 KV-cache quantization arrives through the arena interface of 3.4, which already hides cache dtype and layout behind the opaque handle. Quantized operators enter the rewrite engine as barriers at first: identities valid in real arithmetic do not in general survive quantization boundaries — the same dtype sensitivity the rule validator's mixed-precision testing exists to catch (4.1). On the roadmap: bf16 lands in phase 1; weight-only quantization in phase 4, or earlier as a parallel track; the fp8 cache together with the paged layout.

### 3.2 Debugging Workflow, Control Flow, and the World Boundary

The chief debugging dividend of shallow embedding is that definitions execute directly. Under the eager backend, any layer or subexpression can be called in the REPL with real tensors; printf inside function bodies, Racket breakpoints, and single-stepping all work, because these are ordinary function calls. Layer-by-layer numeric cross-checking against an HF reference implementation becomes natural: run a layer eagerly, compare, move on. The recommended workflow is the one PyTorch users already know — develop and debug in eager, then switch to the tracer to build the graph for the optimizer, same code, one changed parameter. The single asymmetry a user must know: under the tracer, printf prints symbolic placeholders. Branches and loops on tensor values are not an asymmetry — stage-polymorphic control flow lifts them into the graph automatically (below).

The boundary between the graph world and the host world is physical: at runtime, taking a tensor's value means draining the asynchronous device pipeline until that value is readable; at trace time, a symbolic tensor has no value at all. Any abstraction can only choose who sees this boundary and when — LazyTensor hides it inside silent synchronization, JAX turns it into an error, closed tensor languages exclude the host altogether — and this design's choice is to make it explicit, countable, and rare. Crossing happens through exactly one family of operations: `item` (0-d tensor to host scalar, with an element-count assertion) and `fetch` (the host list image under "nesting depth = rank"); comparison operators return 0-d boolean tensors rather than host booleans, so control flow itself never needs to cross. What genuinely crosses is only true host effects — printing, tokenization, token accumulation, termination — and these live naturally between steps in the orchestration layer, where each step's logits are already real tensors. The rule stands: only decision-sized data crosses the bridge; bulk transfers go through CPU tensor views, not through it.

Control flow is stage-polymorphic: the same `if` and loop syntax dispatches on the stage of its condition. A host-valued condition — construction logic — really branches and really loops, unfolding at trace time; this is shallow embedding's existing behavior. A symbolic condition — data-dependent logic — is lifted into the graph by the language itself: `if` sub-traces both arms, unifies their output shapes and dtypes, and emits graph-if; loops lift to graph-while — the loop-carried state is the binding list, so the triple of condition subgraph, body subgraph, and initial values is read directly off the source (exactly what lax.while_loop makes users assemble by hand), one body trace decides shape stability of the carried state, and tail position is syntactically decidable, so "back edge not in tail position" gets a precise diagnostic; fixed-length sweeps emit scan. In implementation, the liftable loops form a bounded, blessed set: named let, for/fold, and do receive zhulong-provided expansions that all desugar to one shared loop primitive, so the stage check is written exactly once — one primitive, several idiomatic entrances. The boundary must be stated honestly. Lifting is decided at trace time — whether a symbolic tensor reaches the condition is a runtime fact — so statically rewriting the letrec that racket's own expansion produces is not an option: hygiene binds racket/base's expansion to its own core forms beyond interception, and no static pass can tell a data-dependent loop from a construction loop that must unroll. A bare recursion's back edge is an ordinary function application, invisible to the tracer: data-dependent bare recursion would expand forever through nested graph-if, so a trace depth guard intercepts it — lifting is abandoned and the enclosing expression falls back to an island in the usual auto-eager way, with the report naming the cause and suggesting named let / for/fold. Chez's tail-call optimization is orthogonal: it runs trace loops in constant stack but tells the tracer nothing about back edges — execution optimization and graph-construction decisions live on different levels. Compare JAX: it likewise cannot jit a bare Python while and demands rewriting into lax combinators; this design's liftable set is bounded too, but the blessed forms are idiomatic Racket rather than foreign combinators, and the lifting is automatic — owning the expander turns lifting into reading the source rather than reverse engineering, the second concrete dividend of choosing Racket after delimited control. The explicit `(graph-if ...)` and `(graph-while ...)` forms remain as assertion variants: same semantics, but failure to lift is an error rather than a fallback.

Above lifting sits an earlier division of labor: **the best in-graph branch is no branch.** Production systems eliminate the branches that matter not with control-flow machinery but with branch-free authoring — mask/padding for variable length and batching, top-k plus gather/scatter for MoE routing — vLLM and SGLang do all of this by hand. This design freezes those idioms into the layer library (the library components of 3.1 are written this way), with correctness held by differential testing; it is the primary mechanism, and it is human-written — the high-value branch-to-dataflow reconstructions (padding layout, routing restructure) are global structural decisions beyond the reach of local rewrite rules, and are not pretended into eqsat. The three-tier division is then clean: branch-free authoring (layer library, hand-written) eliminates the branches that matter; automatic lifting (the language) takes the genuinely control-flow residue — speculative decoding's accept decision, early exit, certain sampling constraints, concentrated and small; lowering (the optimization plane, below) picks implementations for the lifted nodes, where "rewrite a graph-if with pure, cheap arms into select" legitimately exists as a local rule but is minor cleanup.

The language emits control-flow nodes of this project's own IR; choosing an implementation is a lowering decision in the optimization plane, walking a ladder by backend capability and cost. Where the pinned torch version supports it, lower through its control-flow higher-order operator family (cond/while_loop/scan/associative_scan/map, semantics preserved through torch.compile and torch.export) into AOTI — cond is the most mature, and from 2.12 it can stay inside CUDA-graph capture via conditional graph nodes (CUDA 12.4+). Where branches are cheap, lower to select — both arms execute and a mask chooses, available everywhere, with guards against division-by-zero and NaN in the untaken arm. Where neither works, fall back to an island. Language-side lifting is thereby decoupled from backend maturity: each time an upstream higher-order operator stabilizes, the ladder shifts up one rung and model code does not change by a character; when the torch version is pinned, each operator's real AOTI surface is verified and recorded in the version manifest.

Lifting is not always possible: arms whose shapes or dtypes cannot be unified, arms containing host effects, non-tail recursion, carried state that changes shape across iterations (a growing concatenation) — these cases, together with value-taking operations appearing mid-trace, fall to the fallback mechanism, the **eager island**: a region that is not expanded during tracing but recorded wholesale as one opaque node — tensors the region references become the node's inputs, and its product returns to the trace as a fresh symbolic value. At runtime, when execution reaches the node, the executor materializes the inputs, switches to the eager backend, invokes the Racket closure, and feeds the result back into the compiled graph. Islands turn graph breaks from all-or-nothing into locally contained, and pollute neither upstream nor downstream — tensors computed before the block stay in the compiled graph, and tracing resumes normally after it. What must be controlled is how much gets pulled *into* the island: because the backend is a dynamic parameter, everything called within the block enters the island, so the rule remains **decisions in the island, computation outside it**, and the profiler flags any matmul-class operator found inside one. Lifting simply shrinks this rule's jurisdiction: intra-step data-dependent control flow enters the graph by default, and the island returns to its proper name — an escape hatch, not a regular channel.

The key design decision: **users never predict where escapes are needed — auto-eager is always on, not an optional mode.** Data-dependence points that cannot be lifted do not fail silently at trace time; they surface deterministically. A symbolic tensor has no value, so any value-forcing operation necessarily raises a value request in the tracer, precise to the source location. On capturing the request, the tracer automatically marks the smallest enclosing expression as an island and continues the trace. The implementation uses Racket's delimited control directly: the tracer installs a prompt at every DSL expression boundary; when a value request fires, it aborts to the nearest boundary — discarding only that expression's execution state — registers the island node, and resumes the trace seamlessly through the continuation captured at the boundary. One pass, no restart. First-class delimited control is a primitive of the host language; the equivalent in the Python stack requires heavyweight bytecode-level graph-splitting machinery. This is one of the concrete dividends of choosing Racket. An island's output shapes are established by a placeholder probe execution at trace time; the rare case of data-dependent output shapes requires explicit annotation.

One scoping fact deserves precise statement. Tracing itself does not depend on `#lang zhulong`: operators are generic functions dispatched on the backend parameter, so code in plain Racket modules — project helpers, third-party libraries — records graph nodes normally, and its loops and higher-order functions compose as usual. What the `#lang` governs is prompt placement, and with it how tightly an automatic island can be scoped. The smallest-enclosing-expression guarantee holds for code expanded under `#lang zhulong`; when a value request fires inside a function defined in a plain module, the nearest prompt lies outside that call, and the island grows to the whole call. The degradation is visible rather than silent — the trace report shows every island's extent, and the profiler's matmul-inside-island warning covers the one genuinely harmful case, a hot-path helper mixing a value-dependent branch with heavy operators — and the remedy is mechanical: move the helper into a `#lang zhulong` module, or hoist the heavy operators out of the branch. The convention is that model code lives under `#lang zhulong`; interop with plain Racket remains fully supported and costs only island granularity.

Visibility is guaranteed by two companion facilities, shifting the burden from annotating in advance to seeing afterwards. First, the **trace report**: after every trace, a list of islands — location, triggering cause (including why lifting failed), estimated per-token cost — with hot-path islands escalated to prominent warnings; the report also carries the constant audit of 3.1: every constant baked into the graph, with its provenance. Second, the trace stage can emit **the DSL source with `with-eager` inserted**: not an abstract graph rendering but legal DSL code — the user's own code, verbatim, with each automatic island explicitly wrapped in `(with-eager ...)`. A diff against the original shows every break at a glance, and because the output is adoptable code, the user can paste it back to solidify implicit islands into explicit declarations (this echo shares infrastructure with explain-optimization). Production-regression protection rests on the report: CI compares island lists across trace reports and catches silent performance regressions. This upholds the principle behind our critique of torch.compile's silent breaks: the problem there is that breaks happen without the user's knowledge, not that the user didn't write them by hand.

### 3.3 Graph IR and Provenance

The optimization pipeline is one-directional: the DSL is traced into graph IR; eqsat performs semantics-preserving optimization on the IR; planning and scheduling attach communication and execution annotations; finally the graph is partitioned into compiled subgraphs and interpreted glue. The optimizer consumes and produces IR — an S-expression graph annotated with types and shapes — and never writes back into the DSL. The DSL is the definition layer for humans; the IR is the transformation substrate for machines; the responsibilities stay separate.

Two mechanisms bridge the human and machine views. **Provenance annotations**: every optimized node retains a chain pointing back to its DSL definition. Writable hot reload depends on provenance for incremental invalidation, and during debugging any runtime tensor can answer "which source line did I come from." **Pseudo-DSL echo**: since the IR is S-expressions, pretty-printing it as pseudo-DSL is nearly free; `(explain-optimization)` renders the before/after graphs as a diff — a debugging tool, and equally a window for auditing whether an LLM-proposed rule did something foolish.

### 3.4 State Modeling: the KV Cache

The central state of autoregressive inference is the KV cache, and it must be modeled explicitly at the graph level; otherwise rewriting, compilation, and hot reload all break against it. The design principles: **pure-functional semantics, destructive implementation, pluggable layout.**

At the IR level, state is threaded explicitly. A single forward step has the signature `(step params cache token) → (logits cache')`: the cache is an explicit input and output, the function remains pure, and consequently tracing, rewriting, and provenance are untouched by state; state operators like `(kv-append cache k v)` are ordinary graph nodes. The cost of pure semantics is that a naive implementation copies the whole cache every step, which is unacceptable. Hence a linearity constraint: cache values are annotated as linearly consumed, verified by a dataflow-analysis pass over the IR — each cache value is consumed exactly once, and the old handle is never referenced after an update. On an explicit graph this is a trivial analysis. Once verified, the runtime may update in place safely: the optimizer sees a pure function; the hardware runs a destructive write. To be emphatic: this check has nothing to do with the host type system. The IR is our own language and the checker is a graph pass we write; Racket stays dynamically typed and Typed Racket is not needed. The DSL layer uses contracts as runtime guards, and debug mode can add reference-count assertions. Futhark's uniqueness types and Koka's FBIP are the theoretical precedents for "pure semantics, in-place implementation" — we borrow the idea, not their type systems. One further obligation follows: the discipline must survive optimization — how the rewrite engine is kept from disturbing it is specified in 4.1.

At the layout level, the cache is an opaque handle. IR operators face only the logical view — append per layer, read by position; the physical layout is an implementation choice of the runtime arena. Paged layout is the industry standard (established by vLLM, adopted broadly); welding a contiguous layout into the IR and runtime would make later retrofit invasive, so the interface reserves the block-table indirection today. Phase one implements contiguous layout (sufficient for single-request use); the paged implementation lands together with continuous batching and prefix sharing when the orchestration layer takes on multi-request scheduling — with no rework required. The interaction between hot reload and state is handled here as well: if redefining a layer changes the cache layout (head count, precision), the provenance system folds cache compatibility into invalidation — keep if compatible, migrate if migratable, otherwise recompute the prefix and say so explicitly.

## 4. The Optimization Plane

### 4.1 The Rewrite Engine: Equality Saturation and the Rule Ecosystem

Graph optimization uses equality saturation rather than a sequential pass pipeline. Principle and motivation are given in Appendix A; in one sentence: rules apply non-destructively to an e-graph, all equivalent forms coexist, and after saturation a cost model extracts the optimum — dissolving the phase-ordering problem at the root. The implementation follows egg's rebuilding and e-class analysis, with the core data structures rebuilt in Racket; Tensat has demonstrated the method's viability for tensor graphs.

One boundary is drawn before any rule runs: **equality saturation operates only on the pure regions between state operations; the state chain itself is never rewritten.** The reason is a semantic mismatch, not an implementation convenience. A rewrite rule is validated under the IR's pure semantics, in which `kv-append` returns a fresh value and the old cache still exists; whether a program admits in-place implementation is a property of the mutable world — of read/write ordering — and the two worlds do not agree on which programs are interchangeable. The mismatch is concrete. The linearity discipline threads the cache through reads precisely to pin the read-before-write order; under pure semantics a read leaves the cache unchanged, so the rule "the cache before a read equals the cache after it" is unimpeachably true — randomized testing on immutable tensors cannot reject it — yet applying it merges the two handles into one e-class, dissolving exactly the ordering the threading encodes, and extraction is then free to schedule the append before the read, which under a destructive implementation reads overwritten memory. Duplication and deletion are cruder failures of the same kind: a right-hand side that replicates a subterm containing a state operation leaves one cache version with two downstream owners entitled to overwrite it; one that drops such a subterm loses an update. The defense has two layers. First, the cut: the graph is partitioned at state operations, only the pure segments enter the e-graph, and state nodes stand as rigid boundaries. This is the same cut as the layer-wise partitioning adopted below for scale — each transformer layer performs exactly one append — so one mechanism serves both purposes, and the forgone cross-append fusion is negligible, kv-append being a copy into a slot. Second, the fuse: the linearity pass of 3.4 re-runs on every extracted program before it is accepted, and under ILP extraction the single-consumer property can be encoded directly as a constraint. Effect-token threading in XLA/StableHLO and JAX's exclusion of state from jitted pure regions are the same answer to the same question.

Rules are designed as data, not code. A rule defined by `(defrule name pattern => replacement :when condition)` is serializable and hot-loadable, and the e-graph's evolution can be observed step by step in the REPL. The initial library is hand-written, and it is deliberately enumerated early — as a design artifact of the foundation phases, before the engine that runs it exists — because the rule vocabulary and the IR's operator granularity are co-designed: whether softmax is one node or a decomposition, whether rms-norm is a primitive, whether a fused attention operator is kept as a rewrite target — the soundness of these IR decisions can only be judged against the rules that must match over them. Four families seed the library: algebraic simplification, fusion patterns, layout and transpose pushing, and attention-family-specific rewrites.

Every rule, hand-written or proposed, passes the same validation gate: syntax, type, and shape checks first; then numeric cross-checking that executes both sides of the rule on the eager backend and compares results. The test generator is condition-directed rather than uniformly random — it derives cases from the rule's own pattern and `:when` condition: dimensions drawn from boundary sets (0, 1, primes, exact divisibility, off-by-one), size-1 dimensions to force broadcasting, values seeded with 0, ±inf, NaN, denormals, and cancellation pairs (a ≈ −b, which expose floating-point reassociation errors that uniform sampling passes within tolerance), each rule re-run under fp32/bf16/fp16, plus negative tests that generate condition-violating inputs and assert the rule declines to match. The generator shares its skeleton with the differential-testing harness of phases 1–2 (eager versus graph execution cross-checked on the same programs); the rule mode is an added front end, and the whole runs as routine CI over the rule library. The one parameter demanding care is the tolerance policy: per-dtype thresholds, plus explicit tags for rules that are floating-point-unsafe by nature.

LLM-in-the-loop rule proposal — candidate rules generated from the operator vocabulary, the current library, and an optimization objective — remains the intended growth mechanism and is deliberately deferred to the long term. Nothing about the deferral is structural: rules are data, so a proposed rule enters the same gate as a hand-written one without touching system code, and eqsat guarantees that a validated-but-useless rule costs at most search time — the cost model simply never selects it at extraction. The neurosymbolic thread stays; the schedule simply puts first the hand-written library that must exist regardless.

The principal risk is scale: real model graphs reach tens of thousands of nodes, and e-graph growth plus GC pressure is the bottleneck; extraction compounds it, since optimal extraction over a DAG with sharing is NP-hard — Tensat's resort to ILP extraction exists for precisely this reason. Countermeasures, in order: partitioned optimization by transformer layer (saturate within blocks, propagate across — the same cut that isolates the state chain, and it bounds extraction as well as saturation); tiered rule scheduling (cheap rules converge first); and if necessary, sinking the e-graph core data structures into C behind the FFI — always preserving the elasticity of "Racket defines rules and strategy; the underlying structure may sink."

### 4.2 Parallel Planning and Communication Scheduling

Multi-device automation splits into two independent passes, each answering its own question.

The **planning pass answers "where."** Following Alpa: intra-operator parallelism (tensor sharding) is solved as an integer linear program; inter-operator parallelism (pipeline partitioning) by dynamic programming. Input is the graph IR plus a cluster description (devices, memory, interconnect topology); output is sharding annotations and device assignments. After planning, communication is materialized as first-class IR nodes: all-reduce, all-gather, send/recv enter the graph explicitly, and every communication operator splits into a start/wait pair, making asynchrony explicit — the representation validated by XLA's latency-hiding scheduler and PyTorch's communication-reordering passes.

The **scheduling pass answers "in what order, on which stream."** Communication/computation overlap is at heart resource-constrained DAG scheduling — compute streams and communication streams are two resource classes — which is not eqsat's territory of semantics-preserving transformation, hence a separate pass. The objective: hoist starts as early as possible, sink waits as late as possible, fill the gap with computation. Algorithmically, heuristic list scheduling first, ILP refinement later; the communication cost model begins with closed-form estimation (traffic derived from sharding rules, time from topology bandwidth) and is later calibrated by measurements from the tuning loop. Critical-path bottlenecks found by the scheduler can feed back to the planner and trigger re-sharding; the two passes share one IR annotation scheme.

The staging commitment stays honest: the planner first guarantees correct, non-overlapped distributed execution; single-node multi-GPU tensor-parallel overlap and pipeline microbatch scheduling come after; cross-node work (NCCL integration, distributed debugging) is a steep engineering increment and is deferred to the long term.

### 4.3 Parameter Search: the Tuning Loop

Parameter search surrounds the pipeline rather than sitting inside it. It covers compile-time parameters (fusion granularity, tile sizes) and serving-time parameters (batch ceilings, cache allocation, parallelism configuration), and supplies measured calibration data to the rewrite and scheduling cost models. Parameter spaces are declared as S-expression schemas; search strategies (grid, Bayesian, evolutionary) are pluggable; evaluation is by FFI-measured runs or cost-model estimation. The component is deliberately thin — it serves the closed loop and does not aspire to general AutoML.

## 5. The Execution Plane

### 5.1 The FFI Bridge

Binding targets PyTorch's official Stable C ABI first (available since 2.9: the AOTI C shim underneath is a pure C interface; torch::stable wraps it; binary compatibility across versions is an official commitment). It is the ideal target for ffi/unsafe: no name mangling, no C++ templates, no exceptions across the boundary. Its known limitation: currently a limited subset designed for the custom-operator scenario, with operator coverage still expanding. The bridge is therefore two-tier, and the load-bearing order must be stated honestly: today the wrapper tier carries the eager path, and the Stable C ABI is the destination it retires into. Tier one binds the Stable C ABI — tensor lifecycle, metadata, device and stream management, and the operators it exposes. Tier two is an auto-generated thin C wrapper (isomorphic to tch-rs's torch-sys, generated from ATen declarations) covering what the stable surface does not yet reach — which today is most of the operator set the eager backend needs. The wrapper is accordingly a first-class phase-1 deliverable, not a patch. Its scope is manifest-driven — the transitive operator closure of the target model family's eager forward pass plus sampling and cache operations, on the order of tens of operators for the Llama family — and the manifest drives generation. Generation needs libtorch headers and a C++ toolchain at build time only, the same gcc-class build dependency as the compilation sidecar; none of it enters the distribution, and wrapper entries retire one by one as official coverage grows. Tensor ownership is managed explicitly on the Racket side: a with-tensor macro delimits lifetimes, finalizers backstop leaks. Acceptance criterion: load a 1B-class open model running natively in bf16, run it forward layer by layer, and match an fp32 HF reference within per-layer tolerances (3.1).

### 5.2 Dual-Mode Execution and the Compilation Service

Every subgraph can switch between two modes: interpreted execution (operator by operator through the FFI into libtorch) and compiled execution (loading a precompiled artifact). One mechanism serves three purposes: interpretation covers for compilation not yet ready; with-eager islands naturally run in interpreted mode; and it is the downgrade path for writable hot reload (5.5).

Compiled artifacts come from the compilation service. torch.compile is a Python API while the project's hard constraint is native distribution; the resolution is to position Python as a **build-time compiler daemon** — invoking it no more creates a runtime dependency than invoking gcc does. Racket sends a to-be-compiled subgraph (S-expression IR) to a Python sidecar process. Because the operator vocabulary is aligned with ATen, the sidecar can mechanically code-generate the IR into an FX graph or a small nn.Module and compile it through AOTInductor (torch.export plus AOTI) into a .so/.pt2 artifact. The architectural coincidence that makes this clean: AOTI artifacts expose exactly a C interface, of the same Stable C ABI family the bridge already binds — Racket dlopens the artifact and calls it via FFI, with no Python at runtime. Artifacts are cached by subgraph content hash: hit → compiled execution; miss → interpretation covers, an asynchronous compile request is issued, and the artifact is swapped in seamlessly when ready. For distribution, all artifacts for the target model are precompiled and packaged with the native binary; the sidecar exists only on development machines and in the build pipeline. During development, a resident Python process may offer fast RPC compilation to shorten waits; it never enters the distribution path. The known coupling risk — sidecar torch version, AOTI artifact, and Stable C ABI must match as a triple — is handled by pinning the triple in the build pipeline and recording checksums in artifact metadata.

### 5.3 The Multi-Stream Task-DAG Executor

The scheduler's output needs a runtime that can execute a multi-stream plan. The project already has a "subgraphs plus glue" execution model; it generalizes into a multi-stream task-DAG executor: Racket drives CUDA streams and events through the FFI, compiled subgraphs launch on compute streams, communication kernels on communication streams, events express cross-stream dependencies. The division of labor: coarse-grained scheduling belongs to the brain (Racket launches according to plan); fine-grained fusion belongs to AOTI (kernel quality inside subgraphs). Correctness is guarded by keeping a single-stream serial mode as both a debug switch and a numerical baseline: any divergence under multi-stream execution can be localized immediately.

On the decode hot path the executor adds one further mechanism: whole-step CUDA-graph capture. A decode step launches hundreds of small kernels and repeats with identical shapes for thousands of steps — precisely the profile in which per-launch CPU overhead, FFI transit, and Racket GC pauses dominate, and precisely the profile capture rewards. After warm-up, the executor records the step's complete launch sequence once and thereafter replays it with a single call per token, removing the Racket runtime from the per-kernel path entirely. Capture has two prerequisites, both already secured elsewhere in the design: shape stability across steps (the decode shape policy of 3.1) and stable device addresses, since the recording bakes pointers in — the contiguous max-len arena satisfies this trivially, and a paged arena satisfies it through device-side block-table indirection, where replays change table contents but never pointers, as vLLM has validated. The recording is invalidated by hot reload, by any shape change, and by an island or graph-while appearing inside the step — a captured sequence cannot pause to inspect host data. graph-if is the exception: lowered to torch.cond, it can stay inside the capture via conditional graph nodes (torch 2.12+, CUDA 12.4+), a capability that enters the lowering cost model (3.2). This gives the profiler's island warning a second justification beyond lost fusion: an island on the decode path forfeits capture. Prefill is deliberately left uncaptured: its shapes rarely recur, and its few large kernels amortize launch overhead on their own.

### 5.4 The Stream Orchestration Layer

Orchestration models autoregressive generation as a lazy stream: the forward step is the unfold generator, the cache rides along as linear state, and sampling policies, stopping conditions, and beam branches are all stream transformers. A combinator library in the SRFI-41 style — map, take-while, merge, fork, backpressure — expresses three families of scenarios: single-request pipelines (constrained decoding, early exit, the two-stream formulation of speculative decoding), multi-request scheduling and merging (a declarative model of continuous batching, at which point the paged cache arrives), and agent workflows (LLM call chains and demand-driven tool invocation — lazy dataflow by nature). The orchestration layer is built entirely on the system's own runtime and unfolds stage by stage with the capabilities beneath it: single-request pipelines land with compiled execution; multi-request scheduling lands with parallelism and the paged cache.

### 5.5 Observation and Hot Reload: a Tiered First-Class Capability

This is the system's signature capability relative to the Python/C++ stacks, delivered in two tiers to contain complexity.

**Tier A is the read-only observation window, delivered first.** No model modification, pure observation: probes attach and detach at any point in the generation stream — activation statistics, KV-cache inspection, conditional breakpoints into the REPL when attention entropy crosses a threshold; any layer can be re-executed eagerly for cross-checking; profiling runs alongside. Probes are themselves stream transformers, so attaching one does not interrupt generation. Tier A depends only on the eager backend and stream combinators and entirely avoids the complexity of the writable path — no provenance invalidation, no versioned images, no artifact-cache coherence.

**Tier B is writable hot reload, deliberately deferred until provenance exists.** Redefining a layer takes effect in a running system: affected subgraphs are precisely invalidated through provenance, execution downgrades to interpretation to preserve semantics, recompilation proceeds in the background through the compilation service, and the new artifact swaps in seamlessly when ready — the "modified means interpreted, stable means compiled" downgrade/upgrade cycle, which is image-based Lisp development translated into the GPU era. On top of it: online A/B — hot-swapping sampling policies or switching between equivalent implementations produced by the rewrite engine, with live measurement, so the cost model calibrates itself on real workloads. Engineering constraints: artifact caches invalidate precisely by content hash; until in-flight batches complete, modifications apply only to new requests (versioned model images, MVCC-like); distributed hot update is out of scope initially — single-node hot reload, whole-cluster rolling updates otherwise.

## 6. Relation to Existing Work

Relative to torch.compile/AOTI/Triton, this system sits upstream: the Racket layers make the graph-level decisions — rewriting, sharding, scheduling, tuning — and the results land through AOTI, reusing Inductor's and Triton's kernel generation without introducing a second compiler IR. Relative to vLLM/SGLang, there is no competition on production throughput: the system's own execution path serves research and observation, and their ideas — paged attention, continuous batching — are re-expressed declaratively in the orchestration layer. Relative to egg/Tensat, the algorithms are borrowed; the differences lie in the rule DSL's expressiveness, the interactive workflow, and the LLM-in-the-loop mechanism. Relative to JAX/XLA, the ideas are cognate — pure functions, transformations, sharding annotations, latency hiding — while the differences are the "graphs as data" symbolic stance, the observable, mutable runtime image, and syntax-level automatic lifting of control flow (the combinator rewrites lax.cond/while_loop demands are performed by the language here). Relative to Futhark/Koka, the linear-semantics idea is borrowed for state modeling without importing their type systems. Relative to Lush, the project salutes the "Lisp in service of neural networks" lineage — Torch descends from it — but no longer asks Lisp to carry numerical computation itself.

## 7. Roadmap: Bottom-Up

The roadmap depends on no external inference API; every phase rests on the previous phase's foundation, and every phase's output is independently useful.

**Phase 1 — Foundation.** The FFI bridge (Stable C ABI bindings plus the manifest-driven wrapper generator, itself a first-class deliverable), the safetensors loader, the minimal model DSL (both backends, bf16-native), and cache linear threading (contiguous layout). Deliverable: a Llama-family small model defined natively in Racket, its eager forward pass matching an fp32 HF reference layer by layer within declared tolerances, packaged by raco exe into a native, interpreted-execution inference binary; the embryo of tier-A observation (eager probes) appears here, and the initial rewrite-rule library begins as a design artifact reviewed against the IR operator set (4.1).

**Phase 2 — Compilation.** The compilation service runs the full IR → FX → AOTI → dlopen chain; dual-mode execution and the content-hash artifact cache are in place; the shape policy of 3.1 is exercised end to end — static decode, AOTI dynamic dimensions for prefill — and whole-step CUDA-graph capture lands on the decode path (5.3). Deliverable: a compiled-execution native inference binary demonstrating the "interpretation covers, compilation swaps in" loop; tier-A observation ships complete; the single-request streaming pipeline lands as the combinator library's first application; the differential-testing harness (eager versus compiled cross-checking) becomes routine CI, ready to take on the rule-validation front end in phase 3.

**Phase 3 — Optimization and the Writable Image.** The eqsat rewrite engine (running the rule library enumerated in the earlier phases), provenance, explain-optimization, with comparative numbers against a torch.compile baseline; automatic lifting of stage-polymorphic control flow with its lowering ladder (graph-if/graph-while/scan, 3.2); tier-B writable hot reload.

**Phase 4 — Parallelism and Serving.** The planning pass (correctness first, no overlap); the scheduling pass and the multi-stream executor (single-node multi-GPU overlap, pipeline microbatching); orchestration takes on multi-request scheduling, and the paged cache plus continuous batching land; weight-only quantization (int8/int4) and the fp8 KV cache land here as well — the former may move earlier as a parallel track if resources allow, the latter arrives together with the paged layout.

**Long term.** Cross-node distribution, the direct Triton emission path, LLM-in-the-loop rule discovery, and training with automatic differentiation.

## 8. Risk Register

Technical risks and countermeasures. Stable C ABI operator coverage growing more slowly than hoped, leaving the wrapper tier load-bearing for longer — accepted openly: the wrapper is a first-class deliverable, auto-generated, manifest-scoped to the target models' operator set, and pinned per torch version. E-graph scale — partitioning, tiered rules, sinkable core (4.1). The semantic-alignment bug surface of IR → FX code generation — per-operator translation unit tests with numeric cross-checks. Backend maturity of the control-flow higher-order operators (cond/while_loop/scan), still officially prototype — the lowering ladder (cond → select → island) decouples language-side lifting from the backend, and each operator's AOTI surface is verified at version-pinning time. The expressiveness boundary of the linearity check (too strict rejects legal programs; too loose breaks in-place safety) — enable it only for cache-class state, no whole-language linear types; the same pass doubles as the post-extraction gate of 4.1. Artifact-cache and hot-reload coherence — content hashing, versioned images, provenance-driven invalidation, biased toward conservative invalidation; deferring tier B is itself risk reduction. Multi-stream executor correctness — the single-stream serial mode as baseline. CUDA-graph capture validity — invalidation conditions enumerated (hot reload, shape change, in-step islands or graph-if), with fallback to per-launch execution. Version-triple coupling — pipeline pinning plus metadata checksums.

Ecosystem risks: the Racket numeric and systems library gaps may exceed expectations; LLM-assisted Racket writing is less reliable than for mainstream languages — countered with strict style guides and structural checking, for which S-expressions are the easiest possible target.

The positioning risk is the largest: overlap with what torch.compile already does. The defense is that every phase must answer "why can't existing tools do this" — and the observation window plus hot reload are structurally impossible in the Python stack (torch.compile recompiles in minutes and is non-interactive). This is the project's least replicable value, and it takes priority whenever resources conflict.

The probing strategy for island output shapes (semantic limits of placeholder probing; annotation form for data-dependent shapes). How the eqsat cost model absorbs measured data without breaking extraction monotonicity. The validation tiers for LLM-proposed rules. The relationship between the orchestration layer's stream abstraction and CSP-style channels under true concurrency. The coordination protocol for multi-node hot updates. Whether AOTI dynamic-dimension kernels for prefill hold up against bucketed static specialization (3.1 keeps both paths pending measurement). The granularity of the pure-region partition around state operations, should a layer ever carry more than one state operation (4.1). The tolerance policy for numeric validation under bf16 — the per-dtype thresholds shared by reference parity and rule cross-checking. The nesting-depth limit and subgraph-scale governance of lifted control flow. Numeric guards for the untaken arm under select lowering. The automatic transform of boundedly growing loops (shape-changing carried state) into preallocation plus masking. How the lowering capability model evolves with the pinned torch version. The granularity and noise control of the constant audit. The coverage of the blessed loop forms (whether more are needed beyond named let, for/fold, and do) and the shared loop primitive's interface. The threshold and diagnostic shape of the bare-recursion trace depth guard. Each is left to be answered experimentally in its phase.

## Appendix A: Equality Saturation in Brief

Traditional compilers organize optimization as sequential passes: each rewrite rule destructively modifies the program, discarding the old form. This creates the phase-ordering problem — the order of rule application affects final quality, and applying one rule may permanently destroy another's match. Example: from `(a*2)/2`, strength reduction first yields `(a<<1)/2`, after which the "multiply-by-y, divide-by-y cancels" rule can no longer match, and the simplification to `a` is lost; the optimal order is unknowable in advance.

Equality saturation inverts the approach: never rewrite, only accumulate equivalences. The central data structure, the e-graph, organizes nodes into equivalence classes (e-classes); all expressions in one class are known semantically equal, and subexpression sharing stores exponentially many equivalent programs compactly. The process has three steps: insert the original program; repeatedly apply all rules at all matching positions, each application merely adding the new form to the appropriate e-class while retaining the old, until saturation (no new facts) or budget exhaustion; finally, a cost model selects the best representative in each e-class and extracts the optimal program bottom-up. Because nothing is destroyed, rule order no longer affects the outcome — every reachable equivalent form ends up in the graph, and choice is postponed to extraction, when information is complete.

The project's motivation for adopting it: rule interactions in tensor-graph optimization are intricate — fusion, algebraic simplification, and layout transformation unlock and shadow one another — so sequential pipelines demand careful manual ordering and still miss opportunities. Eqsat reduces the problem to "define the rules and the cost model, let search speak," and closes the loop with LLM rule discovery: a new rule is merely data entering the library, with no pass ordering to redesign. The price is e-graph space and time, addressed in 4.1.
